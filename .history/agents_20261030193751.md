# Diretrizes Arquiteturais e Estruturais do Projeto

Este documento serve como a única fonte de verdade (SSOT) para o desenvolvimento, arquitetura, segurança e governança de código da aplicação. Toda a equipe e agentes de IA devem seguir rigorosamente estas definições.

---

## 1. Stack Tecnológica Base

- **Core:** React 19+ (ou versão estável corrente) com TypeScript.
- **Build Tool:** Vite (rápido, baseado em ESM nativo).
- **Estilização:** CSS Modules combinado com Sass (`.module.scss`).
  - *Premissa Obrigatória:* Todo arquivo CSS/Sass deve utilizar **seletores aninhados (nested css)** por padrão para garantir escopo isolado e legibilidade.
- **Utilitários Globais:** Tailwind CSS pode ser utilizado exclusivamente para utilitários globais, tokens de layout raiz ou prototipagem rápida de layouts estruturais na raiz.
- **Deploy & Infra:** Vercel.

## 3. Diretrizes de CSS e Estilização

1. **Escopo:** Elementos de design de negócio específicos ficam dentro da pasta do próprio componente utilizando CSS Modules.
2. **Aninhamento (Nested CSS):** O uso de pré-processadores (Sass) exige que o código utilize o padrão de aninhamento para refletir a árvore do DOM do componente.
   * *Exemplo Obrigatório:*
     ```scss
     /* Button.module.scss */
     .container {
       display: inline-flex;
       padding: var(--spacing-md);

       .icon {
         width: 16px;
         height: 16px;
       }

       &:hover {
         background-color: var(--color-primary-hover);
       }
     }
     ```

## 4. Arquitetura Serverless (Vercel Functions)

Para se adequar às limitações físicas e de plano da infraestrutura da Vercel, aplicamos a seguinte governança para APIs:

- **Limite Estrito:** O projeto aceita o limite máximo de **12 Funções Serverless ativas**.
- **Estratégia de Roteamento Baseado em Recursos (Monolithic Functions):** Para evitar estourar o limite de 12 funções, não criaremos um arquivo por rota/ação (Ex: `createUser.ts`, `deleteUser.ts`). Em vez disso, agruparemos por recurso dentro de uma mesma função controlada por métodos HTTP (`GET`, `POST`, `PUT`, `DELETE`).
- *Exemplo de Estrutura Interna de uma Serverless Function (`src/api/users.ts`):*
  ```typescript
  export default async function handler(req: Request) {
    const { method } = req;
    switch (method) {
      case 'GET': return handleGetUsers(req);
      case 'POST': return handleCreateUser(req);
      default: return new Response('Method Not Allowed', { status: 405 });
    }
  }
  ```

## 5. Práticas de Segurança Obrigatorias

1. **Variáveis de Ambiente:** Nunca injete strings de credenciais (`secret_keys`, tokens) diretamente no código. Use `import.meta.env.VITE_APP_...` no client e `process.env` no ambiente serverless. Tudo deve ser configurado diretamente no painel da Vercel.
2. **Sanitização de Inputs:** Qualquer dado de entrada vindo do usuário via formulários deve ser validado e sanitizado no client e revalidado obrigatoriamente no serverless utilizando bibliotecas estruturais (como `Zod` ou `Yup`).
3. **Segurança de Cabeçalhos (Headers):** Configurar políticas de segurança rígidas no arquivo `vercel.json`, incluindo `Content-Security-Policy (CSP)`, `X-Frame-Options` para evitar Clickjacking e `X-Content-Type-Options`.
4. **Armazenamento Seguro no Client:** Tokens de autenticação (JWT) de longa duração não devem ser expostos no `localStorage`. Prefira cookies configurados com `HttpOnly`, `Secure` e `SameSite=Strict` via Serverless API.

## 6. Governança de Deploy e Performance (Vercel)

- **Ignorar Arquivos de Documentação:** Para otimizar o tempo de build, economizar banda e evitar exposição desnecessária de arquivos de governança, todos os arquivos markdown (`.md`), documentações locais e histórias do Storybook devem ser explicitamente listados no arquivo `.vercelignore`.
- **Politica de Cache:** Páginas estáticas ou respostas de APIs que não mudam frequentemente devem implementar cabeçalhos `Cache-Control: s-maxage` para aproveitar as bordas da CDN da Vercel.

## 7. Governança de Internacionalização (i18n)

Para garantir que a aplicação seja totalmente traduzível no futuro, fica estritamente proibido o uso de strings de texto fixas (hardcoded) diretamente nos arquivos de componentes (`.tsx`). 

### Diretrizes de Implementação
1. **Ferramental:** Utilizar `i18next` e `react-i18next`.
2. **Separação por Namespaces:** As traduções não devem ficar em um único arquivo gigante. Elas devem ser divididas em arquivos `.json` por contexto (namespaces), como `common.json` (global), `auth.json` (autenticação), `dashboard.json`, etc.
3. **Padrão de Nomenclatura (Keys):** Use chaves descritivas em formato `camelCase` ou `snake_case`. Evite chaves genéricas que possam gerar ambiguidade.
4. **Carregamento Inicial:** O arquivo `src/i18n/index.ts` deve ser importado logo no topo do arquivo `src/main.tsx` para garantir que os dicionários estejam carregados antes da renderização do App.

### Exemplo Prático de Aplicação

#### Arquivo de Tradução (`src/i18n/locales/pt-BR/auth.json`):
```json
{
  "login": {
    "title": "Boas-vindas de volta",
    "submit_button": "Entrar na conta",
    "errors": {
      "invalid_credentials": "E-mail ou senha incorretos."
    }
  }
}
```

#### Uso correto no Componente React (`src/modules/auth/pages/LoginPage.tsx`):
```tsx
import { useTranslation } from 'react-i18next';
import { Button } from '../../../design-system/components/atoms/Button/Button';

export const LoginPage = () => {
  // Carrega o hook apontando para o namespace específico do módulo
  const { t } = useTranslation('auth');

  return (
    <main>
      <h1>{t('login.title')}</h1>
      {/* Todo conteúdo textual passa pela função t() */}
      <Button variant="primary">{t('login.submit_button')}</Button>
    </main>
  );
};
```

### Regra de Validação para Code Review e IAs
- **Proibido:** `<span>Entrar na conta</span>` ou `<Button>Enviar</Button>`
- **Obrigatório:** `<span>{t('auth:login.submit_button')}</span>` ou `<Button>{t('common:actions.send')}</Button>`
